## 0. 文档目的

设计文档（framework/）回答"这个游戏是什么"，本文回答"用什么技术把它做出来"。方法是从设计铁律反推技术约束，让每一条架构决策都能指回一条设计支柱——凡是不能指回的，都是过度设计。

## 1. 设计铁律 → 技术约束

| 设计铁律（出处） | 技术约束 |
|---|---|
| 框架与内容解耦（白皮书 §2） | 逻辑层不得 import 任何内容数据；内容全部以数据包形式在运行期加载 |
| 呈现与逻辑解耦 / 一核两壳（白皮书 §7.3） | 逻辑层**零引擎依赖**（纯托管代码，可在控制台跑测试）；引擎只出现在渲染壳 |
| 事件流是唯一输入（白皮书 §6） | 追加式事件日志（append-only event log）作为逻辑层唯一对外通道 |
| 状态板唯一真相（白皮书 §4.2） | 单一可变 store；一切写入带溯源（provenance），支撑历史卷轴因果链 |
| 存档 = 状态板快照（白皮书 §4.2） | 状态板全量可序列化；版本化；可迁移 |
| 规则深度是扩展轴（05 文档） | 规则包 = 接口背后的可替换策略集，D20 最小核硬编码在核内 |
| 付费模式是扩展轴（06 文档） | 权利 = 状态板全局变量；商店/活动/成就只是不同的写入方 |
| 内容可持续投放（白皮书 §10） | 内容包独立版本、运行期加载、向后兼容、上线前自动校验 |

## 2. 引擎选型

### 2.1 选型标准（按本项目权重排序）

1. **移动双端（iOS/Android）发布管线成熟度**——含包体、补丁、商店合规；
2. **内容包动态加载能力**——DLC/热更是框架生命线（白皮书 §10），引擎必须有官方或事实标准的资源包机制；
3. **UI 重度 + 2D 为主的表现需求**——九类界面闭环、竖屏三段呼吸布局、斜 45° 伪 3D；不需要 3A 级 3D；
4. **逻辑层可剥离**——支持把核心逻辑写成不依赖引擎的纯类库（决定测试成本与"一核两壳"能否成立）；
5. **团队招聘与生态**——中文社区、人才市场、插件生态。

### 2.2 候选对比

| 维度 | Unity 6 LTS（C#） | Godot 4.x（C#/GDScript） | Unreal 5 | Cocos Creator |
|---|---|---|---|---|
| 移动管线 | ★★★ 最成熟 | ★★ 可用，坑在商店签名与合规细节 | ★★ 过重，包体大 | ★★ 国内成熟 |
| 内容包加载 | Addressables / AssetBundle，官方方案 | **PCK 包天然即 DLC**，最优雅 | DLC 支持笨重 | 热更方案成熟 |
| UI / 2D | UI Toolkit + uGUI，成熟 | Control 节点体系，轻量顺手 | UMG 偏重 | 强 |
| 逻辑层剥离 | **.NET Standard 类库，最干净** | C# 可剥离，GDScript 不可 | 困难 | 一般（TS 可测） |
| 人才生态 | ★★★ | ★★（增长中） | ★★ | ★★（国内） |
| 风险 | 许可政策历史波动 | 移动重度项目案例较少 | 杀鸡用牛刀 | 长线 3D 表现力弱 |

### 2.3 建议（待 M0 技术冻结拍板）

- **主推：Unity 6 LTS + Addressables**。理由：逻辑层可做成零依赖的 .NET 类库（铁律 2 的最佳保障），Addressables 覆盖内容包投放，招聘与生态风险最低。
- **备选：Godot 4（C# 通道）**。若团队规模 ≤5 人且接受生态风险，PCK 即 DLC 的模型与本框架的内容包哲学几乎一一对应，包体与授权成本最低。
- 排除：Unreal（超重）、Cocos（伪 3D 表现与长线内容包规模存疑）。

> **待裁决 E-1**：引擎最终拍板，阻塞技术原型启动，不阻塞本稿其余部分评审（架构设计对两个候选均成立）。

## 3. 总体架构：一核两壳的技术落地

```
┌─────────────────────────────────────────────────────────┐
│ 渲染壳（引擎层）                                            │
│  ├─ 横屏空间渲染器   ├─ 竖屏时间渲染器   ├─ 九类界面 UI       │
│  └─ 骰子演出 / 镜头 / 音频                                 │
│        ▲ 只消费事件流 + 只读状态板                           │
│        │ 只下发玩家意图（Command）                           │
├────────┴────────────────────────────────────────────────┤
│ 逻辑核（纯类库，零引擎依赖，可控制台运行）                      │
│  ├─ WorldStateBoard  世界状态板（§4）                       │
│  ├─ EventStream      事件流总线（§5）                       │
│  ├─ StoryGraph       故事有向图运行时：触发器扫描（§7）       │
│  ├─ EncounterSM      遭遇状态机：六态（§6）                 │
│  ├─ RulePackHost     规则包宿主：D20 最小核 + 可替换策略     │
│  ├─ EntitlementGuard 权利门槛检查（只读状态板权利变量）        │
│  └─ SaveSystem       快照 / 版本迁移（§9）                  │
├─────────────────────────────────────────────────────────┤
│ 内容层（纯数据，运行期加载）                                  │
│  内容包（战役/子游戏） + 规则包 + 权利声明 → 格式见 02 文档    │
└─────────────────────────────────────────────────────────┘
```

关键约束：

- **依赖单向**：内容层 ← 逻辑核 ← 渲染壳。逆向引用在编译期就应不可能（分层程序集 / 模块边界），不靠自觉。
- **逻辑核可在无引擎环境运行**：全部单元测试、分支图校验器、战役全流程仿真（bot 自动试玩）都在控制台执行——这直接服务 TASKS P1.2 的"全流程内部试玩"：原型 UI 之前就能用仿真跑通《烬港残页》35 节点。
- **渲染器对规则档位无感**（05 文档 §6）：渲染壳只认事件流格式，不认规则包。

## 4. 世界状态机（WorldStateBoard）

### 4.1 数据结构

```
Board = Map<NamespacedKey, TypedValue>

NamespacedKey = "<namespace>.<name>"   例：campaign01.seen_fading
namespace ∈ { global, <pack_id> }       全局变量归 global，内容包变量归包 ID
TypedValue ∈ { Bool, Int, Float, Enum, String, List, Set }
```

六类变量（旗标/声望/时间钟/物品/羁绊/倾向）不是六种结构，而是**同一套键值之上的六个语义标签**——标签供 UI 分组与校验器检查使用，存储与读写路径统一。物品持有以 `Set<item_id>` 存于状态板，背包 UI 只是它的视图（04 文档 §1）。

### 4.2 写入 API 与溯源

```
board.write(key, value, provenance: { event_id, node_id, pack_id })
```

- 每次写入**必须携带溯源**（哪条事件流的哪条事件写的）。这是历史卷轴"旗标追溯"（04 文档界面⑧）的数据来源，不加溯源的写入在 Debug 构建中直接报错。
- 写入触发 `StateChanged` 通知 → 故事图运行时的**触发器扫描**（§7）与 UI 刷新都只订阅这个通知。

### 4.3 快照与存档

- 存档 = `Board` 全量序列化（JSON）+ 元信息（框架版本、各内容包/规则包版本、事件流尾部序号）；
- 版本迁移：快照带版本号，加载时按迁移链逐级升级（与规则包"进行中战役冻结旧版本"机制配合，05 文档 §7）；
- 云同步与多周目继承 = 快照的传输与裁剪，无额外机制。

## 5. 事件流（EventStream）

### 5.1 事件结构

```
Event = {
  id,            // 递增序号（存档内唯一）
  session,       // 遭遇 ID（哪一局产生的）
  type,          // check.result / damage.dealt / flag.written / ...
  payload,       // 结构化数据（骰值、修正、难度、结果……）
  source,        // 产生者（规则包 / 遭遇状态机 / 故事图）
}
```

### 5.2 架构性质

- **追加式、不可变**：事件一旦写入不得修改。渲染、日志、历史卷轴、成就、回放消费同一条流（白皮书 §7.3）；
- **进程内发布订阅**：逻辑核产出，渲染壳订阅。战斗等高频场景按"节拍"批量投递（一次行动的所有事件一帧内到达，供渲染器组织演出节奏）；
- **确定性**：逻辑核内一切随机（骰子、战利品 roll）走**种子化 RNG**，种子入存档。事件流 + 种子 = 可完整复盘的单局；
- **回放是纯演出**：战报回放（04 文档界面⑧）直接重播事件流驱动渲染器，不重跑逻辑、不可改结果。

### 5.3 为什么不用 ECS / 消息队列中间件

单机体量下事件流就是一条有序列表加订阅回调，刻意保持朴素：它首先是**档案数据结构**（历史卷轴、回放、成就、调试日志的公共真相源），其次才是通信机制。引入中间件只会模糊这一性质。

## 6. 遭遇状态机与规则包宿主

### 6.1 遭遇状态机（EncounterSM）

六态（白皮书 §6）实现为显式状态机而非行为树/协程散点——状态数少、转换需要被校验与可视化：

```
进场 → 探索 ⇄ 发现 → 战斗 → 结算 → 休整 → 出场
                └→ 对话 ─┘   └─→（撤退边）→ 出场
```

- 每个状态进入/退出条件来自内容包遭遇定义（02 文档），状态机本体无内容；
- 状态切换即竖屏"呼吸"布局的驱动信号（04 文档 §④.1）：状态机向外发 `state.entered` 事件，渲染壳据此调整三段高度——**逻辑从不指挥界面，界面只是订阅状态**。

### 6.2 玩家输入：Command

渲染壳只下发意图（`MoveCommand` / `AttackCommand` / `ChoiceCommand` / `RollCommand`……），逻辑核校验合法性后执行并产出事件。非法意图直接拒绝——渲染层 Bug 不会污染逻辑状态。

### 6.3 规则包宿主（RulePackHost）

D20 最小核硬编码于核内（检定公式骨架、事件流输出、状态板读写，对应 05 文档 §2 三条不可变项）；六要素以接口注入：

```
interface IRulePack {
  AttributeModel   Attributes   // 属性模型（轻：3 维；深度：类 5e）
  CheckFormula     Check        // 修正计算与难度标定
  ActionEconomy    Economy      // 每回合可做什么
  TurnStructure    Turn         // 先攻与回合循环
  GrowthCurve      Growth       // 升级获得
  DeathRule        Death        // 归零处理
  AttributeMapping MapTo(other) // 跨规则包角色转换（05 文档 §5）
}
```

- 战役加载时按其声明的规则包 ID + 最低版本绑定（存档记录绑定版本，进行中战役冻结）；
- 角色界面的字段集由当前 `IRulePack.Attributes` 驱动生成（04 文档界面⑦"动态呈现"）。

## 7. 故事有向图运行时（StoryGraph）

- 内容包把五类边编译为统一的**条件 + 目标 + 效果**结构（02 文档 §4）；运行时无"五种边"的概念，只有条件求值器——边类型只是给内容作者与 UI 呈现的语义标签；
- **触发器扫描**：每次状态板写入后，对当前活跃节点集合的出边做一次条件求值，点亮/熄灭节点。扫描是增量的（只复查引用了被改变量的边），35 节点 ~200 边量级下开销可忽略；
- **时间边**由 Doom Clock 写入触发同一扫描，无独立计时器体系；
- 分支图校验器（死路 / 不可达 / 旗标闭环 / 节点预算 / 命名空间冲突）是**独立命令行工具**，与逻辑核共享同一份求值代码——保证"校验通过"与"运行正确"语义一致。

## 8. 内容包运行时与加载管线

```
加载流程：读取 manifest → 框架版本检查 → 命名空间注册（冲突检查）
        → 权利门槛检查（EntitlementGuard，只读）
        → 图与表结构校验 → 索引建立 → 可玩
```

- **Unity 通道**：Addressables 远程目录，每个内容包一个 group；规则包同机制；
- **Godot 通道（备选）**：每包一个 PCK，`ProjectSettings.load_resource_pack`；
- 版本三方解耦（框架 / 内容包 / 规则包），内容包声明 `min_framework_version`，框架保持向后兼容（PRD F5.2）；
- 格式细节、校验清单、制作流程见 `02-内容包格式规范.md`、`03-内容包制作操作指南.md`；首个实例：`../story/campaign01/`（《烬港残页》全量数据化）。

## 9. 存档、回放与多周目

| 能力 | 实现 |
|---|---|
| 存档 | 状态板快照 + 事件流尾部 + 绑定版本表（§4.3） |
| 回放 | 事件流重播（§5.2），纯演出不可交互 |
| 多周目 | 新周目 = 新快照 + 从旧快照按"继承清单"选择性拷贝（继承清单本身是内容包数据，见战役书 §11 开放项） |
| 失败不重读档 | 结构上不存在"读档重来"的必要——失败已写板并进分支（白皮书 §5.2）；存档点仅作退出保护 |

## 10. 技术原型计划（对应 TASKS"全流程内部试玩——待原型阶段"）

| 阶段 | 交付 | 验证目标 |
|---|---|---|
| TP0 逻辑核骨架 | 状态板 + 事件流 + 求值器，控制台可跑 | 铁律 2/3/4 成立 |
| TP1 战役仿真 | 加载 `story/campaign01/` 数据，bot 自动跑通 35 节点全结局 | 内容包格式完备性 + 分支图校验器 |
| TP2 单遭遇竖屏壳 | 引擎内一场竖屏战斗 + 三段呼吸布局 + 掷骰演出分级 | 一核两壳、事件流驱动渲染 |
| TP3 双壳验证 | 同一遭遇横竖两壳各跑一遍，事件流逐字节比对 | 数据零差异（白皮书 §7.3） |
| TP4 闭环 | 主屏 → 战役入口（模式分支）→ 遭遇 → 结算 → 历史卷轴追溯 | 九类界面最小闭环 |

TP1 不依赖引擎选型（逻辑核在任一候选引擎下都是 .NET 类库），**可以先于 E-1 裁决启动**。
